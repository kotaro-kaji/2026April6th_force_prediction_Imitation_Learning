**ChatGPT**

方針としては、完全に2ネットワーク化するより、まず「共有表現＋複数head」または「単一world-model内の複数loss」に寄せて設計したほうが、研究仮説がきれいになります。関連する近い研究系統も確認しつつ、設計案として整理します。

設計上いちばん重要なのは、実行時に更新する対象を「PB / latent property だけ」に固定し、policy 本体は更新しないことです。ここを守れば、world model と policy を完全分離しなくても仮説は崩れません。

結論としては、 **完全に別ネットワークを2つ持つより、共有 encoder/backbone + world-model head + policy head の構成がよい** と思います。  
ただし、最初から完全 joint training するより、 **段階的に学習して、最後に軽く joint fine-tuning** するのが安全です。

あなたの案で本当に必要なのは、2つの機能です。

1. **内部物性表現 z を同定・更新するための未来予測機能**
2. **z に条件づけて行動を出す policy 機能**

これは別ネットワークである必要はなく、次のようにできます。

```
observation encoder:     E(o_t, force history, proprio)
temporal backbone:       T(E(...), action history, z_t)

world head:              future latent/image/force prediction
policy head:             diffusion policy / flow policy for action
```

つまり、

```
h_t = T(E(o_{≤t}), a_{<t}, z_t)

world head:
  ô_{t+1:t+H}, f̂_{t+1:t+H} = W(h_t, a_{t:t+H-1}, z_t)

policy head:
  a_{t:t+H-1} ~ π(h_t, z_t)
```

この形がかなり自然です。Diffusion Policy 自体は、action sequence の多峰的な分布を扱いやすいことが強みとして示されていますし、視覚条件つきのロボット操作 policy として使いやすいです。 [^1] 一方で、shared encoder + task-specific heads は multi-task learning で一般的な hard parameter sharing の形で、隠れ層を共有し、出力層だけタスクごとに分ける設計です。 [^2]

重要なのは、 **実行時に backprop する対象を z、つまり PB / latent property だけに限定する** ことです。policy head や encoder までオンライン更新すると、単なる test-time fine-tuning になってしまい、研究の主張がぼやけます。

## おすすめの学習手順

### Phase 1: world model + PB の学習

まず、デモA/Bを区別せずに使って、

```
L_world = prediction loss of future image/latent + force
```

で、

```
E, T, world head, object-wise z_i
```

を学習します。

ここで z\_i は、オブジェクトごとの nn.Embedding でよいです。これは RNNPB 的な発想にかなり近いです。RNNPB 系では、PB を通じて行動パターンや対象差を内部表現として扱い、さらに PB 更新で状況変化に対応する方向の研究があります。 [^3]

ただし、未来画像そのものを pixel-level で予測すると重くなります。最初の実験では、

```
future visual latent
future force / torque
object pose / slip / tilt
gripper displacement
```

を予測するほうがよいと思います。未知重心タスクなら、画像よりも **力・モーメント・傾き・滑り・接触後の微小運動** のほうが内部物性を強く反映します。

---

### Phase 2: デモBに対して causal に z\_t を作る

ここはかなり大事です。

デモBの開始時点では、

```
z_0 = mean(z_1, z_2, z_3)
```

としてよいですが、offline で z\_t を作るときも、 **未来を見すぎない** ようにしたほうがよいです。

つまり、時刻 t で z を更新するときは、

```
observed: o_{t+1}, force_{t+1}
used action: a_t
prediction: world_model(o_{≤t}, a_t, z_t)
```

の誤差だけで、

```
z_{t+1} = z_t - α ∇_z L_world
```

とする。

こうして得た

```
(o_t, z_t) → a_t
```

を policy 学習用データにする。

ここで H-step future を丸ごと使うと、offline では可能でも、実行時にはまだ観測していない未来を使って z を更新することになります。研究としてきれいにするなら、 **実行時と同じ情報制約で z\_t を生成する** べきです。

---

### Phase 3: policy head を学習

この段階で、

```
E, T を共有
policy head を追加
```

します。

policy の loss は、

```
L_policy = diffusion policy loss / behavior cloning loss
```

でよいです。

デモAでは、

```
z_t = z_object
```

固定。

デモBでは、

```
z_t = online-adapted z_t
```

を使う。

これにより、policy は次を学習します。

```
z が曖昧 → 探索行動
z が同定済み → すぐタスク実行
```

ただし、単に mean vector だけを入れると、policy がそれを「中間物性の既知オブジェクト」と解釈する危険があります。よりよいのは、

```
z_t
uncertainty_t
```

を両方入れることです。

例えば、

```
z_t = posterior mean
u_t = posterior variance / entropy / number of adaptation steps
```

のようにする。すると policy は、

```
z が平均値だから探索する
```

ではなく、

```
内部物性の不確実性が高いから探索する
```

を学習できます。

これはかなり重要です。未知物性同定の研究としては、 **mean PB だけより、belief / uncertainty を持たせたほうが主張が強い** です。

---

## joint training は「あり」だが、最初から全部混ぜないほうがいい

あなたが言っている、

> encoder は共有して、output head だけ分けて、交互に両方の head で学習

はかなり良い方向です。

実際、world modeling と action prediction を shared backbone + 2 heads で扱い、test-time training / adaptation に使う方向の研究も出ています。WorldAgen は、world modeling と action prediction を shared Transformer backbone と2つの head で統合し、test-time training によって新しい環境に適応するという構成を取っています。 [^4] また、Diffusion Policy に補助的な future/state reconstruction loss を足す Crossway Diffusion も、policy 学習に予測的な補助 objective を組み合わせる方向として近いです。 [^5]

ただし multi-task learning では、複数 loss の gradient が衝突することがあります。shared encoder + task-specific heads は一般的な構成ですが、タスク間の干渉や loss balancing が問題になることがあります。 [^6]

なのでおすすめはこれです。

```
Stage 1:
  world model + PB を学習

Stage 2:
  encoder/backbone を一部 freeze して policy head を学習

Stage 3:
  L = L_policy + λ L_world
  で軽く joint fine-tuning

Execution:
  network weights は固定
  z のみ online update
```

つまり、 **共有するが、学習は段階的** がよいです。

## 最終的な推奨アーキテクチャ

```
Inputs:
  image / visual latent
  force-torque
  gripper state
  action history
  latent property z_t
  optional uncertainty u_t

Shared:
  visual-force encoder E
  temporal backbone T

Heads:
  1. world head
     predicts future latent/image/force
     used for PB learning and online PB update

  2. policy head
     diffusion policy / flow policy
     predicts action sequence
```

loss は、

```
L = L_policy + λ L_world + β ||z_t - z_prior||^2
```

実行時は、

```
θ_E, θ_T, θ_world, θ_policy: frozen
z_t: updated online
```

です。

## ただし、3オブジェクトだけだと弱い

実証実験としては3種類でも始められますが、論文としてはやや弱いです。

3つだけだと、policy が

```
object 1
object 2
object 3
```

を覚えているだけに見えやすいです。

できれば、外観は同じで内部重心だけ変わるオブジェクトを作って、

```
train: CoM positions 1,2,3,4,5,...
test: held-out CoM positions
```

にしたほうがよいです。

特に良い設定は、

```
外見は同じ
内部重心だけ違う
視覚だけでは識別不能
接触・持ち上げ・力応答でのみ識別可能
```

です。

この設定なら、あなたの研究仮説である、

```
探索行動によって内部物性表現をオンライン更新し、
同定後は即座に適切な操作へ移る
```

がかなり明確になります。

## まとめ

あなたの直感どおり、 **完全に別ネットワークを2つ用意するより、共有 encoder/backbone + 別 head のほうがよい** です。

ただし設計としては、

```
world model と policy を同時に最初からごちゃ混ぜに学習
```

ではなく、

```
1. world model + PB を先に作る
2. PB online adaptation trajectory を作る
3. policy head を学習する
4. 最後に world loss を補助 loss として joint fine-tuning
```

が一番きれいです。

研究の核は、

```
policy が探索を学ぶこと
```

ではなく、

```
world prediction error によって latent physical property が更新され、
その latent state を policy が使って探索から実行へ切り替えること
```

に置いたほうが強いです。

```
h_t = T(E(o_t), z_t)

a_t:t+H = policy_head(h_t, z_t)
```

このとき、

```
E, T: frozen
policy_head: trainable
```

です。

ただし、これだと policy head が少し窮屈な場合があります。その場合だけ、次の順で緩めるのがよいです。

```
Option 1: policy head only train

  recommended if performance is poor

Option 3: policy head + upper layers of T train
  possible, but PB空間が崩れるリスクあり

Option 4: E/T/W も全部 train
  最初は非推奨
```

私なら、Stage 3 はこの形にします。

```
freeze:
  visual-force encoder E
  temporal backbone T
  world prediction head W
  object PB table z_i

train:
  policy diffusion head π
  maybe small FiLM/adaptor layers for policy only
```

より実用的には、共有 backbone から policy へ入る直前に小さな adapter を置きます。

```
h_world = T(E(o_t), z_t)

h_policy = Adapter(h_world, z_t, uncertainty_t)

a_t:t+H = π(h_policy)
```

Stage 3 では、

```
train:
  Adapter
  policy head π

freeze:
  E
  T
  W
  PB
```

がかなり良いです。

その後の Stage 4 で、joint fine-tuning するなら、

```
freeze:
  PB z_i は基本 freeze か、かなり小さいLR
  world head W は freeze でもよい

  policy head π
  adapter
  temporal backbone T の一部

  L = L_policy + λ L_world
```

```
  keep: L_world as regularizer
```

それで性能が足りなければ、policy adapter を追加して train するのが一番きれいです。
